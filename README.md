# 艇王 BOATRACE ROYAL

ボートレースの出走データを自動で収集し、統計モデル(ロジスティック回帰)で各艇の1着確率を推定して**3連単の買い目と賭け金配分を自動生成**するWebサービスです。

> 予想(予測順位・1着確率・買い目)はすべて統計モデルの計算によるもので、生成AIは使っていません。
> 生成AI(Groq の `openai/gpt-oss-20b`)を使っているのは、予想結果をもとにしたレース解説文の生成だけです。

## プロジェクト概要

ボートレースは全国24場で毎日開催される公営競技です。1レース6艇が出走し、**3連単**（1〜3着の着順通りの予想）は最大120通りの組み合わせがあります。

艇王は以下を自動化します。

- **データ収集**: boatrace.jp・mbrace.or.jp から出走表・直前情報・オッズ・レース結果を自動スクレイピング
- **予想(統計モデル)**: 選手成績・コース別成績・直近成績・展示タイム・モーター性能・気象データをロジスティック回帰モデルに入力し、各艇の1着確率と予測順位を算出
- **買い目生成**: Harville式確率（3連単の着順確率）に基づき、4種類の戦略で買い目を自動生成
- **賭け金配分**: モデルの予測確率に比例した傾斜配分（1点最低100円保証）
- **レース解説(生成AI)**: 予想結果(予測順位・確率・選手データ)を Groq API(`openai/gpt-oss-20b`)に渡して解説文を生成(`gemini_explain.php`。ファイル名は旧実装の名残で、Gemini は使っていない)
- **成績分析**: 回収率・的中率の累積集計、レーサー別・会場別統計

## 主要機能

### 予想(統計モデル)

各艇の1着確率をロジスティック回帰モデルで算出し、確率の高い順を予測順位とします。本番では2つのモデルを使い分けています(切り替えは `model_switch.php`)。

| 用途 | モデル |
|---|---|
| 予想表示(予測順位・確率・解説文の元データ) | **v3w** |
| 買い目: 的中特化・バランス・絞り込み | **v3w** |
| 買い目: 一撃重視 | **v2** |

- **v3w**(`predict_v3_core.php`、22特徴量): 枠番、全国・当地勝率、展示タイム(レース内相対値)・展示ST・モーター2連率(相対値)、風速・波高、平均ST・レース内ST順位、コース別成績(ベイズ平滑化)、直近10走の成績、級別。勝者サンプルを枠番の事前確率で重み付けして学習(本命寄りを緩和)
- **v2**(`predict_v2_core.php`、11特徴量): 枠番、全国・当地の勝率・2連率、展示タイム・展示ST・モーター2連率、風速・波高・気温
- v2・v3w の予測は全レースで両方保存しており、参照モデルの予測が無いレースは v2 で買い目を作ります
- 当地成績・コース別成績はレース日より前のデータだけで集計します(結果の先読み防止)

予測確率は100点満点のスコアに換算して表示し、枠番・スコア・成績推移をカード形式で一覧します。

### 4戦略の買い目生成

Harville式確率（$P(a \to b \to c) = P_a \cdot \frac{P_b}{1-P_a} \cdot \frac{P_c}{1-P_a-P_b}$）で3連単確率を算出し、上位から買い目を選択します。

| 戦略 | 選定方法 | 点数 |
|---|---|---|
| **的中特化** | 予想上位5艇の3連単60通りから Harville 確率の高い順に15点(2026-11-05 のレースから。それ以前は上位4艇から9点) | 15点 |
| **バランス** | 予想1・2位を1着に固定 × 上位4艇から2・3着(3連単オッズ100倍超は除外) | 最大12点 |
| **一撃重視** | 予想1位を1着に固定 × 2〜4位から2・3着(3連単オッズ15倍未満は除外) | 最大6点 |
| **絞り込み** | 予想上位3艇の3連単6通りから Harville 確率の高い順に3点 | 3点 |

点数・対象艇数・オッズ条件は `generate_strategies.php` の定数(`TOKKA_POOL_SIZE` / `TOKKA_POINTS` / `BALANCE_MAX_ODDS` / `ICHIGEKI_MIN_ODDS`)で1か所から変更できます。予測確率が使えないレースは、確率を使わない従来の選び方(的中特化=上位3艇の全順列6点、絞り込み=枠番順1点)にフォールバックします。

### 傾斜配分（2026年9月9日導入）

1点均等（100円）を廃止し、モデルの予測確率に比例した傾斜配分を採用しています。

- **基準予算**: 1点平均600円（例: 的中特化15点 → 合計9,000円）
- **最低保証**: 全買い目に最低100円を保証（的中機会ゼロを防止）
- **配分方式**: 確率比例 + Largest Remainder法で100円単位に整数化
- **定数**: `STAKE_SCHEME='prob'`・`STAKE_UNIT=600`・`STAKE_MIN=100`（1箇所で変更可能）

### 成績分析

- 戦略別の的中率・回収率・損益(全体・日別/週別・会場別・会場横断)
- レーサー別成績・コース別勝率・会場別統計
- 「今日の的中」: 当日(結果取込み前は前日)の的中をレース単位で一覧(オッズ・人気・的中した戦略のアイコン)
- 2026-08-19〜09-28 は結果取込み後の再計算で成績が実際より高く記録されていたため、公開ページの集計から除外しています(`data_quality.php` の `PUBLIC_EXCLUDE_LEAK_PERIODS`)
- プラン別: Free（レース場一覧・データ分析の一部）→ Standard（予想の閲覧・成績の詳細）→ Premium（スコア内訳・戦略比較ビュー・マイ的中トラッカー）。一覧は `plan-features.js`

## 自動化ジョブ一覧

### `boatrace.yml` — 定期データ取得

| 実行時刻 (JST) | ジョブ | 内容 |
|---|---|---|
| 毎朝 7:00 | `scrape_beforeinfo` | 全24場の出走表・直前情報（展示タイム・ST・モーター等）を取得しDBへ投入 |
| 毎朝 7:00（並列） | `scrape_odds_a/b/c` | `scrape_beforeinfo` 完了後、当日全レースの3連単オッズを3並列で取得（JCD 01〜08 / 09〜16 / 17〜24） |
| 毎日 14:00（並列） | `scrape_odds_evening_a/b/c` | 夕方〜夜レース分のオッズを再取得（朝時点で未確定のオッズの取りこぼし対策） |
| 毎夜 20:00 | `fetch_results` | **前日分**レース結果を取得・清算(21:30 バッチが失敗・遅延した日の補完) |
| 毎夜 21:30 | `fetch_results` | **当日分**レース結果を取得・清算（strategy_results に is_hit/cost/payout を記録） |
| 毎夜 21:30 | `backfill_missed_beforeinfo` | live.yml の取りこぼし分の直前情報を一括補完（boatrace.jp は翌朝まで保持） |

`fetch_results` の手順:

1. `generate_strategies_for_date.py` で対象日の全レースの予想・買い目を事前生成(閲覧されていないレースも漏れなく清算するため)
2. `api_v3_shadow.php` で v3w 予測の補完生成(事前生成で保存できなかったレース分)
3. `download_results.py` で競走成績を取得・清算
4. 検証用CSV(`data/odds_*.csv` / `payouts_*.csv` / `finish_*.csv` / `lr_v3_*.csv`)をエクスポートしてリポジトリにコミット(下記)

1〜2 は結果取込みの前に行います。結果確定済みのレースの予測・買い目は書き換えません(先読みリーク防止。`prediction_guard_lib.php`)。
GitHub Actions の schedule は遅れて発火することがあり、21:30 のバッチが遅れた場合も 20:00 の前日分バッチで補完されます。
`workflow_dispatch` で `target_date` を指定すると、その日の `fetch_results` だけを再実行できます。

#### 設計判断: 検証データを CSV でリポジトリに蓄積する方式

本番DB（ロリポップの共用サーバー上の MySQL）は、外部ホストからの直接接続を受け付けない構成になっています。そのため開発環境（ローカルPC）から本番DBへ到達できず、戦略シミュレーションや点数比較などのオフライン検証（`strategy_sim.py` / `sim_stake_allocation.py` / `sim_tokka_points.py`）に必要な確定オッズ・払戻・着順・特徴量をローカルで直接取得できないという制約がありました。代替案として「本番DBを外部公開し、ローカルから直接接続する」ことも検討しましたが、共用サーバーのDBにインターネット経由の接続経路を新たに開くことになり、攻撃面が増える・認証情報漏洩時の被害が大きいというセキュリティ上の懸念から採用を見送りました。

採用した方式は、`fetch_results` ジョブ（GitHub Actions）が結果確定後に**読み取り専用のエクスポートAPI**（`export_odds_payouts_v3.php` / `export_lr_data_v3.php`、`API_KEY` 認証）を叩いて日次CSV（`data/odds_*.csv` / `payouts_*.csv` / `finish_*.csv` / `lr_v3_*.csv`）を生成し、リポジトリにコミット・蓄積するというものです。ローカルの検証スクリプトはこの `data/` 配下のCSVを読むだけで動作します。これにより **本番DBへの外部接続経路を一切開けずに**（＝攻撃面を増やさずに）、開発環境で本番相当データを使った検証を可能にしています。CSVはGit管理されるため検証結果の再現性が担保される点も利点です。

### `live.yml` — リアルタイム直前情報・オッズ更新

GitHub Actions の schedule は実際には数時間に1回しか発火しません（throttling）。そのため **cron-job.org** から `workflow_dispatch` で外部トリガーし、実質 **10分間隔**で更新しています(schedule の `*/10` は外部トリガー停止時の保険)。

| 設定 | 値 |
|---|---|
| トリガー | `workflow_dispatch`（cron-job.org 経由、10分間隔） |
| timeout | 15分 |
| 同時実行 | `cancel-in-progress: true`（前のrunが完了しなければキャンセル） |
| 冪等性 | `import_beforeinfo.php` は `COALESCE UPDATE` で既取得分を上書きしない |

### `backfill.yml` — 払戻補正（手動実行のみ）

`is_hit=1` かつ `payout=0` の欠損レコードについて、オッズを再スクレイピングして払戻を再計算します(`backfill_odds_from_gap.py`)。

### `tests.yml` — PHPUnit(Pull Request 時)

`main` への push 時のテストは `deploy.yml` の `test` ジョブで実行します。
